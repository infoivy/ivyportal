# Ivy Portal — Agent Guide

Ivy Portal is the internal operating hub for Ivy Sales Academy. It covers team EOD reporting, student success, revenue and installment tracking, internal knowledge, and founder content planning. Preserve the existing visual design unless a task explicitly asks for a redesign.

## Stack and commands

- React 19, TypeScript, Vite 8, TanStack Start/Router, Tailwind 4, Radix UI, and Supabase.
- Production hosting is Vercel; the canonical domain is `https://portal.ivysalesacademy.com`.
- `npm ci` installs locked dependencies; `npm run dev` starts local development; `npm run build` produces the Vercel/Nitro build.
- Copy `.env.example` to `.env` locally. Browser-safe values use `VITE_`; `SUPABASE_SERVICE_ROLE_KEY` is server/maintenance-only and must never be committed or put in frontend code.
- `npm run roles:grant -- email@example.com role` grants a role after the account exists. `npm run supabase:verify` checks the deployed tables, RLS, and policies using the local service role key.
- Migrations live in `supabase/migrations/`. Link with `npx supabase link --project-ref <ref>` and apply with `npx supabase db push`. Never edit an already-applied migration; add a new timestamped migration.

## Project structure

- `src/routes/`: file-based routes. `_authenticated.tsx` is the signed-in route boundary; individual routes add role checks for their feature.
- `src/integrations/supabase/`: client creation, auth middleware, and generated database types.
- `src/lib/auth-context.ts`: session, profile, and role loading. Use `useAuth()` for UI gates, but enforce sensitive access with Supabase RLS as well.
- `src/lib/`: query helpers and domain logic. `revenue.ts`, `streak.ts`, and the route files hold key calculations and workflows.
- `src/components/`: reusable UI and feature components. Keep it presentation-focused.
- `supabase/migrations/`: complete schema history; `docs/DATABASE.md` explains the current database in plain language.
- `scripts/`: maintenance utilities. They are run locally with ignored `.env`, not in the browser.

## Roles and access

The valid business roles are `admin`, `founder`, `cofounder`, `closer`, `setter`, `csm`, `coach`, and `student`, plus two VIEW-ONLY roles `sales` and `fulfillment` (founder-directed 2026-07-31): they select the department home picture on the dashboard and grant nothing else — never key permissions, EOD expectations, or nav access off them. `cofounder` unlocks the Finance tab (under Sales), the CRM page, the Payouts page, the CSM hub, and fulfillment alerts in the notifications bell; founder-only surfaces (Content, IG analytics) stay founder-only (Gathering Hub was removed 2026-07-12 — Finance absorbed its numbers). Department split (founder-confirmed 2026-07-12): Abu Bilal runs sales; Faizan runs fulfillment. Both were granted the `founder` role on 2026-07-29 (founder-directed: "they're also founders with me") on top of admin/cofounder and their operating roles, so they see everything the founder sees; they KEEP `cofounder`, so the co-founder commission caps still apply to their closes. CRM is ONE page: a Close pipeline summary (counts/values only — working leads happens on close.com) for admin/closer/cofounder plus the Mochi dashboard replica for admin/founder/cofounder. The fulfillment side (Students/CSM/1-on-1 Calls/Testimonials) is one tabbed section behind a single Students sidebar entry. A person may have multiple roles. The first account created in a brand-new database automatically receives both `admin` and `founder`; every later account starts without a role until an admin assigns one. `user_roles` plus the security-definer `has_role` function are the backend source of truth.

UI checks use `const { roles } = useAuth()` and `roles.includes('role')`. Do not treat a hidden button or route guard as security. New tables and storage objects must have RLS enabled with policies that enforce the same server-side rule. Gathering Hub, Instagram/content planning, and founder-only docs are founder-only; founder_settings (operational: cash goal, CRM toggle, quarterly goals) remain admin-manageable. Payment details, revenue, and installment records are closer/admin-only unless a narrower existing policy says otherwise. Whop is the source of truth for cash-in (founder-stated 2026-07-12): the Finance page reads Whop and reconciles it against logged deals/paid installments (amount ±$1 within ±3 days = same money, never summed twice); unmatched items on either side surface as the gap. Setters do not have Sales or Revenue access (founder-confirmed 2026-07-11); their defaults are Dashboard, EODs, Action Items, Calendar, Testimonials, Knowledge, Notes (the Training page was removed 2026-07-25 — Skool hosts training). CSMs can update `students` rows (approve looms → applying, unlock portals, keep phase/status current — founder-directed 2026-07-18); payment records stay closer/admin-only. Service credentials are admin-only.

## Business rules — do not weaken these

- EOD reporting is seven days per week: there are no off days. Founder-role accounts never file EODs and see no EOD surfaces (home EOD blocks hidden, /eods redirects to Performance); `profiles.eod_exempt` (admin toggle on Team) removes any member from every expected-filer surface: home pulse, Performance cards, nudges, daily digest (founder-directed 2026-07-29). Phone setters target 100 dials and 3 sets daily; DM setters target 300 DMs sent and 6 sets daily (raised from 125/3, founder-directed 2026-07-28, effective 2026-07-29; rows before that judge under 125/3 via `kpiTargetsFor` in `src/lib/eod-kpi.ts`); full-cycle setters (both) target 100 dials AND 50 DMs sent AND 3 sets daily. (Founder-approved 2026-07-11: "leads contacted/outreached" folded into "DMs sent" — one field for the same activity. Historical rows keep `leads_contacted`; readers take the max of both fields so old KPI days still count.)
- Setter commission is base percentage plus +1% for top setter in each 14-day period and +1% when that INDIVIDUAL setter collects $5,000+ cash in a Mon–Sun week (not a team total). There is no PIF bonus for setters.
- Closer commission: 10% close-only. The 15% "set + close" rate applies ONLY when the same person both set and closed the deal (`setter_id === closer_id`) — it replaces 7.5% + 10%. A deal set by a different setter pays that setter their base and the closer 10%; setters never close. (Founder-confirmed 2026-07-10; implemented in `src/lib/revenue.ts` `isSelfSet`.)
- Commission payouts run on semi-monthly periods (1st–15th and 16th–end of month, founder-confirmed 2026-07-12). Monthly base pay (`profiles.base_pay_monthly`, e.g. CSM $500) is paid once per month PER MEMBER on their own pay day (`profiles.base_pay_day`, anchored to their start date — founder-corrected 2026-07-28); it belongs to whichever semi-monthly period contains that day, and the FIRST payment lands only after a full month worked (started June 30 → first pay July 30).
- Co-founders who close earn a FLAT 10% — even on set+close — capped at $1,000 per semi-monthly payout period and $2,000 per calendar month (founder-corrected 2026-08-06; the cap was NEVER per Mon–Sun week; implemented in `src/lib/payouts-calc.ts`).
- Profit (Finance page and the split) is computed AFTER team payouts (commissions + base pay), not just after expenses (founder-confirmed 2026-07-12). Finance is founder+cofounder only — admin alone does not unlock money.
- Student flow (founder-directed 2026-07-18, amended 2026-07-25): a new student first confirms their own timezone (soft lock; editable later on Profile), then the portal is LOCKED to the five Start Here steps (onboarding form → join offer board → walkthrough Loom (embedded) → Skool training videos → offer board course; identical for both pathways) until all are done — completion auto-stamps `students.onboarding_completed_at`, advances phase to training, notifies fulfillment (bell + team chat), and auto-assigns 1:1 students the "Book your 1:1 coaching calls" task. After unlock, Start Here is REMOVED entirely. Students see NO phase journey/pipeline language and NO Placements tab (placements are staff-managed). Daily student targets: ALWAYS 3 roleplays; pre-approval 3 looms/day into the Inner Circle Loom Review chat (NOT to offers); after a CSM approves (phase → applying) 5 loom applications/day. Phases (founder-simplified 2026-07-29): onboarding → training → applying → offer_won, plus paused; coaching_1on1 renamed to training (readers stay tolerant of legacy values), testimonial is the `testimonial_collected` flag not a phase, graduated/uncategorized retired; offer_won is terminal and shows the graduation page — the daily EOD shows exactly one loom field per stage, no Replies, no Summary. Weekly EOD sits UNDER the daily one, records WHICH group calls were attended (names from `org_settings.group_call_schedule`, admin-editable, no times) plus self-reported 1:1 calls (they only get `calls_allotted`, usually 10), turns loud from Sunday, and AUTO-SUBMITS from live attendance ticks at ~23:45 Sunday in the student's own timezone (pg_cron `student-weekly-eod-autosubmit`). Students can never DELETE EODs (daily or weekly) — only adjust; deletion is admin/coach/CSM only. Program type derives from `calls_allotted > 0` (1:1) vs 0 (group). Graduated phases (offer_won/testimonial/graduated) owe no EODs and see the graduation page only.
- Content cadence is TOF Monday–Thursday and MOF Friday–Sunday. Record in two-week batches; Thursday is recording day.
- Gathering Hub, Content planning, IG analytics, and founder-only docs are FOUNDER-only (admin does not imply access). Payment details are closer/admin-only.
- Students are never hard-deleted: `students.archived_at` (set by the Archive action, the refund flow's default, or Restore to clear) is what removes someone from every roster and picker while preserving money/EOD history; new student list/picker reads MUST filter `archived_at IS NULL`, and CSM/fulfillment reads that join students filter `students.archived_at IS NULL` too (founder-directed 2026-07-31 after an archived student kept appearing).
- Group-program students (`calls_allotted = 0`) NEVER show 1:1 surfaces anywhere: no assigned coach, no 1:1 tabs/stats/pickers, and no "no 1-on-1" health or at-risk flags (founder-directed 2026-07-31: "make these changes universal"). Gate new per-student 1:1 UI and cadence judgments on `calls_allotted > 0`.
- Historical EOD and revenue records are operational records, not content: do not alter or delete them. ONE founder-approved exception (2026-07-29): admins may UNLOCK a single staff EOD (delete for resubmission, Performance day detail) when a lagging device clock trapped a report on the wrong date; the member resubmits fresh. The EOD form day follows `profiles.timezone` when set, device day otherwise. Add a new correction/adjustment flow if the business needs an audit trail; never silently rewrite history.
- Do not put Supabase service-role keys, access tokens, OAuth secrets, or customer data in git, browser code, logs, or documentation.

## Copy style

Never use em dashes (—) in user-facing text (founder-directed 2026-07-18). Use a period, comma, colon, or the " · " separator instead. Empty-value placeholders in tables use "–" (en dash), not "—".

Never render a raw or exact date for anything within the last two weeks (founder-directed 2026-08-02, universal: staff and student surfaces alike). Every displayed date goes through `friendlyPastDay()` in `src/lib/dates.ts` (Today / Yesterday / weekday / "Last Friday"; short "Jul 10" only beyond two weeks; `humanDue()` for due phrasing). Calendar grids and date inputs are exempt.

## Change discipline

Keep changes small, typed, and migration-backed. Run `npm run build` and `npx tsc --noEmit` after app changes; run `npm run supabase:verify` after a deployment/migration. Preserve RLS. After ANY Supabase write (insert/update/delete/upsert), call `invalidateForTables(qc, [tables])` from `src/lib/query-keys.ts` so every page that reads those tables refreshes; register new query keys and table dependencies there. Keep optimistic setQueryData patches for your own screen only, never another page's cache. New routes reachable by students must be added to the student allowlist in `_authenticated.tsx` or they will be redirected. Use an explicit new migration for schema, policy, function, trigger, or bucket changes. Do not use the service role in client code. Do not change commission rules, role gates, EOD KPIs, or data-history behavior without explicit written approval.
